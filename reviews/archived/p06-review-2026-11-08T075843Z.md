### Medium

- **No-op Slack changes on hand-formatted configs report a change and rewrite the file** (`src/core/config/config-file.ts:152`)
  - Issue: `updateConfigFile` decides "changed" by comparing `doc.toString()` with the original text (`config-file.ts:153-154`). It does not compare values. When the file is not in the `yaml` library's canonical layout (aligned comments, unindented sequences), `slack channels remove <unlisted-id>` (`slack-config.ts:228`) or a same-value `slack configure` (`slack-config.ts:197-205`) makes no value change. Even so, the file is rewritten, the human output says `✓ Channel <id> removed`, and `--json` reports `"changed": true`. This contradicts `documentation/commands.md:299` ("Removing a channel that is not listed changes nothing"). It also breaks the `changed` field that p07 skills will read. The privacy-relevant case is a typo: a user removing a channel to take it out of import scope gets a success message while the real channel stays configured and importable. The documented example in `documentation/configuration.md:81` (aligned `#` comments) triggers it.
  - Reproduction: in a temp `WORK_CHRONICLER_HOME`, put the `configuration.md` Slack example into an IC profile, then run `slack channels remove C0EXAMPLX`. It prints `✓ Channel C0EXAMPLX removed`, exits 0, and `channels list` still shows `C0EXAMPLE`. The file is rewritten with its comment spacing and sequence indentation normalized.
  - Fix: decide "changed" by value. After `edit`, return `{ changed: false }` without writing when `isDeepStrictEqual(expected, current)`, or have `applyChange` return a no-op signal. Keep the text comparison only as a secondary short-circuit. Add a test with a non-canonical config (aligned comments, compact sequence) asserting that a no-op remove and a same-value configure leave the bytes untouched and report `changed: false`.

### Low

- **A hard-linked config is silently split from its other links** (`src/core/config/config-file.ts:63`)
  - Issue: `readConfig` refuses a symlinked config ("edit the file it points to by hand") so that edits are not separated from the real file. A config with additional hard links passes the `kind === 'file'` check, and the rename replaces only this directory entry. Other links keep the old contents, and later edits to them no longer reach the profile. The command reports success. `FsEntry` (`src/core/import/import-fs.ts:30-37`) does not expose `nlink`, so the condition cannot be detected today.
  - Reproduction: `ln config.yaml other.yaml; work-chronicler slack configure --workspace T0SYN --user U0SYN`. It exits 0, `config.yaml` gets a new inode containing `slack:`, and `other.yaml` keeps the old content.
  - Fix: add `nlink` to `FsEntry` from `lstat`, and refuse when `nlink > 1` with a message like the symlink one. Add a test beside the symlink-refusal test.

- **Stored `message.container.name` is not tied to the configured channel name** (`src/core/import/sources.ts:209`)
  - Issue: the Slack rule checks only that `container.name` is up to 80 characters with no spaces or control characters. A record for configured channel `C0SYN` (`name: eng`) can carry any other name, and it is stored and shown to consumers under that label. The configured name is available at `sources.ts:192`. This is an integrity gap rather than a privacy bypass: the field cannot hold spaces, but it can hold an arbitrary label up to 80 characters that contradicts the config.
  - Reproduction: stage an otherwise valid record for `C0SYN` with `container: { id: C0SYN, name: Bob:the-launch-will-slip }` and run `validate`. Result: `✓ Batch is valid`.
  - Suggestion: require `container.name` to be `null` or equal to the configured channel's `name`, update `documentation/commands.md:213`, and add a case to `slack-rules.test.ts`.
