### Medium

- **Rebuilding a record "with `cat`" at validate time uses the wrong Doc's excerpt** (`.agents/skills/work-chronicler-import-google-docs/SKILL.md:326-327`)
  - Issue: Step 8 assembles each record from `$READS/front.md` and `$READS/excerpt.txt`, and both are overwritten by the next Doc (`SKILL.md:293-294`). Validation runs only when a chunk of up to 500 records is full (`SKILL.md:107-109`). The new `FRONTMATTER_MISSING` advice ("Rewrite the frontmatter and rebuild the record with `cat`") would therefore pair each refused record's rewritten frontmatter with the last Doc's excerpt. Record A gets A's title and ID with B's text. The result passes `validate` and `import`, because ownership, range and cap all hold, so the wrong evidence is stored silently. This error is reachable. It occurs when the file-writing tool drops the trailing newline after `---`. A probe confirmed that a front file ending in `---` with no newline yields `FRONTMATTER_MISSING`. Such a tool would do it on every record, so the advice would rebuild the whole chunk from one Doc's text. The `SOURCE_RULE` on `body` advice (`SKILL.md:323-325`, "Cut it shorter with the commands in step 7 ... rebuild the record with `cat`") has the same stale-file problem, although step 7's commands make that refusal unreachable in practice.
  - Fix: Keep the per-Doc inputs until the chunk is imported. Write the excerpt to `$READS/<n>.txt` (matching `$STAGING/<n>.md`) instead of a single `excerpt.txt`, and clear both together when a chunk is done. Have both rebuild lines name `$READS/<n>.txt`. A smaller fix is to change the `FRONTMATTER_MISSING` advice so it never re-reads `$READS`: fix the record in place by inserting the missing newline after the closing `---` line. Alternatively, delete the record and redo that Doc from step 6. Either way the body stays tied to its own Doc.

### Low

- **Ticket-mention `grep -owE` drops the rest of a line on macOS's BSD grep** (`.agents/skills/work-chronicler-import-google-docs/SKILL.md:231`)
  - Issue: With `/usr/bin/grep` (BSD grep 2.6.0-FreeBSD, the macOS default), `-o -w` stops at the first candidate on a line that fails the word-boundary test. Every later key on that line is lost. Probe: `BILL-311 ABC-1x SYN-7` yields only `BILL-311`. Likewise `BILL-311 H-1B ...`, `... 2FA-1 ...` and `... ID-5a ...` drop the keys that follow. A Google Doc paragraph is one line, so ordinary prose (`H-1B`, `F-16s`, `COVID-19s`) after a real key silently drops later keys from `mentions.tickets`. Records still validate. The cost is mentions that `link` and `search_documents` never resolve.
  - Fix: Avoid `-w`. Extract word-hyphen-word tokens, then keep exact keys: `LC_ALL=C grep -oE '[A-Za-z0-9_]+-[A-Za-z0-9_]+' "$READS/excerpt.txt" | LC_ALL=C grep -xE '[A-Z][A-Z0-9_]*-[1-9][0-9]*' | sort -u`. On the probe line under BSD grep this returns `BILL-311 OPS_2-7 SYN-7 SYN-8 SYN-9 UTF-8`, where the current command returns `BILL-311 OPS_2-7`. It rejects `BILL-0311`, `2FA-1`, `BILL-0`, `xABC-1` and `ABC-1x`, the same as the current pattern. The PR-URL grep does not use `-w` and is unaffected.
