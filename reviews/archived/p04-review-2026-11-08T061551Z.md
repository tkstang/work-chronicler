### Low

- **Docs say the next import puts records back when it may instead complete the batch** (`documentation/commands.md:195`)
  - Issue: lines 191-195 cover two cases together: putting a record back failed, and `import` cannot confirm whether the batch was recorded as stored. They end "Run `import` again ... to finish putting the records back." In the second case (`writeCommittedJournal` returns `unknown`, `transaction.ts:1036-1046`) nothing was undone, and the next import may complete the batch rather than restore it. The code's own message says this correctly ("the next import will finish or undo it", `transaction.ts:1042`). Reproduction: `/tmp/wc-rev2/probes.mts` scenario D. The `committed` rename applies and then throws EIO, and the journal read-back fails. The first run gives `ROLLBACK_INCOMPLETE` with records NEW/NEW. Recovery reports `outcome: completed`, so nothing was put back.
  - Suggestion: end the bullet with "to finish the recovery: records are put back, or, if the batch had been recorded as stored, it is kept and reported as completed."

- **Committed-journal conflict message calls a successful import "interrupted" and claims a previous version that does not exist for created records** (`src/core/import/transaction.ts:776`)
  - Issue: the new `RECOVERY_CONFLICT` message says "an interrupted import was recorded as complete ... the previous version and the journal are kept in .import-transaction". Since p04-t06, a `committed` journal with a non-new record arises mainly after a successful import (`ok: true`) whose cleanup failed, followed by a later hand edit or removal. That import was not interrupted. For a `create` operation there is no backup, so no previous version is kept. The docs say "the next `import` finishes the cleanup" (`documentation/commands.md:198`) and describe the conflict only "during or after an interrupted import" (`documentation/commands.md:205`). In this case the next import instead stops with `RECOVERY_CONFLICT`, and imports stay blocked until `.import-transaction/` is removed by hand. That fail-closed behavior is defensible; only the wording is wrong. Reproduction: `/tmp/wc-rev2/probes.mts` scenario E. The batch updates two records and creates one. The sync and the `discardTransaction` rename fail after `committed`, and the first run returns `ok: true` with 2 warnings. The created record is then deleted by hand. Recovery returns `RECOVERY_CONFLICT` for that record, saying its previous version is kept, but `backup/` holds only `0.md` and `1.md`, the two updated records.
  - Suggestion: word the message by operation, for example "an import recorded as complete" and "the journal (and, for a replaced record, its previous version) are kept". Extend the docs bullet at line 205 to cover a record changed after a completed import whose cleanup had not finished, and qualify line 198 accordingly.
