### Low

- **A takeover refusal says the lock names no owner when it names a live run** (`src/core/storage/filtered-subset.ts:689`)
  - Issue: Under the guard, taker C renames the dead owner's lock to `.filter-lock.stale-<id>` (line 688). That frees `.filter-lock`, so a new run D can claim it, and D's `removeLockLeftovers` removes every `.filter-lock.stale-*` as "always unused" (lines 587-589), including C's in-flight copy. C's `readLockOwner(stale)` then returns null. C tries to rename the missing copy back, which fails silently (line 692), and refuses with `lockHeldMessage(lockPath, null)` (line 696): "`.filter-lock` exists but does not say which run holds it … If you know no filter is running …, remove `.filter-lock`". In fact `.filter-lock` is D's readable, live lock. Mutual exclusion holds (D is the only holder, and the subset ends correct). The defects are that C's run fails needlessly and that its message describes the lock wrongly, next to advice to remove a live lock. The existing test for this interleaving (`src/core/storage/filtered-subset.test.ts:642`) checks only the error name, so the wrong text passes.
  - Reproduction: `node_modules/.bin/tsx /tmp/wcrev3-probe/stalegone.ts` prints `C err: …/.filter-lock exists but does not say which run holds it. … remove …/.filter-lock and try again.` and then `lock as status reads it: {…"owner":{"pid":103,…}}`.
  - Fix: When `moved` is null (state `missing`), the stale copy was already cleaned up by whoever now holds the lock. Do not rename it back. `continue` to the next attempt instead, which claims the lock or refuses with `lockHeldMessage(lockPath, <current owner>)`. Keep the rename-back and refusal only for a `moved` that names a different owner, and build that message from a fresh `readLockState(lockPath)`. Extend the "while the stale lock is moved aside" test to assert that the refusal names D's pid rather than "does not say which run holds it".

- **A takeover guard left by a killed run blocks every `filter` and `filter --clear`, with a misleading "try again in a moment"** (`src/core/storage/filtered-subset.ts:676`)
  - Issue: If a run is killed between claiming `.filter-lock.takeover` and its `finally` release (lines 676-707), the guard keeps an owner that has provably exited. When the guard claim fails, the code never checks that owner's liveness (lines 676-681). Leftover cleanup removes a dead guard (lines 590-593), but only after the lock is held, and the lock still belongs to the dead owner it was taking over. Every later `filter` and `filter --clear` is therefore refused with "Another `work-chronicler filter` run (process P …) is taking over .filter-lock from a run that has exited. Try again in a moment." Retrying never helps. `documentation/commands.md:327-328` says a lock left by an exited process on this machine "is taken over", and this lock is not. Recovery does exist: the error says to remove the guard, `status` says to remove `.filter-lock`, and the probe showed both work. The window is a few syscalls, so this is rare.
  - Reproduction: `node_modules/.bin/tsx /tmp/wcrev3-probe/deadguard.ts <tmp>/wl` SIGKILLs a taker right after its guard rename. Three later `replaceFilteredSubset` calls and one `clearFilteredSubset` call each print `… (process 68164 …) is taking over …/.filter-lock from a run that has exited. Try again in a moment. If no filter is running, remove …/.filter-lock.takeover …`. `tsx src/cli/index.ts filter -c <cfg> --clear` prints the same.
  - Fix: When the guard claim fails, read the guard's owner. If `ownerIsAlive(taker, env)` is false, either retire the dead guard the same way the lock is taken over (rename it to a unique name, verify the moved copy still names that owner, remove it, then retry), or refuse with a message saying the guard was left by process P, which has exited, and to remove it, dropping "try again in a moment". Add a test with a dead-owner guard over a dead-owner lock.
