## Summary

The import engine is careful work: it never derives destination paths from record text, opens every file without following symlinks, checks every directory and destination again just before each change, and survives single injected faults and crashes at every write. I found one contract break in the transaction. If the directory sync after the `committed` journal is written fails, the in-process rollback runs while the journal on disk still says `committed`. When that rollback is then incomplete, or its cleanup fails, the next import reports the batch as `completed`. That is wrong in both cases: the work log holds a mix of old and new records, or none of the batch at all, and the backups have been deleted. Separately, schema errors echo unknown frontmatter key names verbatim, which contradicts the documented "never repeat record content" guarantee, and the docs overstate what a failed import guarantees.

### High

- **Rollback under an on-disk `committed` journal lets recovery report a mixed or empty batch as completed and discard backups** (`src/core/import/transaction.ts:946`)
  - Issue: `commitImportPlan` sets `journal.state = 'committed'` and calls `writeJournal` (lines 946-947). `writeJournal` renames `journal.json.tmp` over `journal.json` and then calls `fs.syncDirectory(txn)` (line 408). If that sync throws (any code outside `UNSUPPORTED_DIRECTORY_SYNC`, such as EIO or EMFILE), the `catch` at line 948 rolls back every record, but the journal on disk already says `committed`. If any rollback step then fails, the transaction directory is kept (lines 956-961). The same happens if `discardTransaction` cannot rename it (line 963). On the next import, `recoverInterruptedImport` sees `state === 'committed'` (lines 699-702), deletes the transaction directory with its backups and reports `outcome: 'completed'` ("had already stored all N record(s)"). This breaks the p04 exit evidence ("recovery never reports a partial batch as successful") and the journal's T14 contract ("old or new batch, never a mix"). It also loses the previous version of every record whose rollback failed, because its backup is deleted. I reproduced it with `ImportFs` hooks (scripts below). Variant A: the sync fails after `committed`, then one backup restore fails. The first run returns `COMMIT_FAILED, ROLLBACK_INCOMPLETE` and leaves record 1 OLD, record 2 NEW. The recovery run returns `ok: true`, `recovery.outcome: "completed", records: 2`, the work log stays mixed and `.import-transaction/` (with record 2's backup) is gone. Variant B: the sync fails after `committed`, the rollback succeeds and then the rename in `discardTransaction` fails. The first run says "no records were changed", and the recovery run says all 2 records were stored while both are OLD. Both variants need two faults, or one fault plus a crash during the in-process rollback, but they are the exact destructive path the contract guarantees, and the single-fault and crash loops in `commit.test.ts` do not exercise them.
  - Fix: never roll back while the journal on disk may say `committed`. Option 1 (smallest): every record was already stored and its hash verified before the `committed` journal is written, so move that final `writeJournal` out of the rollback `try`. If the rename succeeded, treat a later sync failure as a warning and return `ok: true`. Option 2: before rolling back after a failure in the final journal write, rewrite the journal to `committing`. If that rewrite fails, return `ROLLBACK_INCOMPLETE` without touching records, so recovery uses markers rather than trusting `committed`. Add a regression test that fails the `syncDirectory(.import-transaction)` call after the `committed` rename, together with (a) one failed backup restore and (b) a failed `discardTransaction` rename. Then assert that the recovery run never reports `completed` unless every record holds its new hash.
  - Requirement: p04 Exit evidence ("recovery never reports a partial batch as successful", "existing records stay intact on rejection"); Outcome 3; journal T14/T17

### Medium

- **Schema issues echo unknown frontmatter key names, contradicting "never repeat record content"** (`src/core/import/record-file.ts:101`)
  - Issue: for `unrecognized_keys`, `describeSchemaIssue` prints every key that matches `^[A-Za-z0-9_.-]{1,64}$` (`printableKey`, lines 55-59). Keys are text from the staged file. The module header says "no text from the file is ever copied into a message" (`record-file.ts:18`), `issues.ts:4` says "An issue never carries record content", and the public contract says "Messages never repeat record content" (`documentation/commands.md:208`) and "issues that never repeat record content" (`CHANGELOG.md:25`). Reproduction: a staged record with an extra top-level key `zebra-quartz-secret: 1` (the suite's own planted `SECRET`) or `alice.smith: 1` yields `{"code":"SCHEMA_INVALID","message":"has unrecognized key(s): zebra-quartz-secret"}`. The existing test (`record-file.test.ts:145`) passes only because it uses `${SECRET} said hi`, which contains spaces and so is not printable. Under the brief's privacy constraint, a skill mistake that writes a person's or channel's name as a key would end up in CLI output and agent logs.
  - Fix: report unknown keys without their text. For example, report "has N unrecognized key(s)", or print a key only when it is in a fixed allowlist of known field names from other record types or versions. Alternatively, narrow every documented guarantee to say plain key names may be echoed. Code and docs must agree. Add a test that plants a printable key such as `SECRET` itself and asserts that it is not echoed.

### Low

- **Docs overstate what a failed import guarantees** (`documentation/commands.md:188`)
  - Issue: "If anything fails or changes on the way, every record already stored is put back and the import reports that no records were changed" (and `CHANGELOG.md:21`, "a failure puts every record back"). When a rollback step itself fails or meets a concurrent edit, the code reports `ROLLBACK_INCOMPLETE` / `RECOVERY_CONFLICT` with "restoring the previous records is not finished" (`transaction.ts:813-816`), and the CLI says "the work log needs recovery" (`import.utils.ts:231`). The docs describe the conflict case only for recovery after an interruption, not for the in-process rollback.
  - Suggestion: add one sentence saying that if putting a record back also fails, `import` reports `ROLLBACK_INCOMPLETE` or `RECOVERY_CONFLICT`, keeps `.import-transaction/`, and the next `import` retries. Soften the CHANGELOG line to match.
