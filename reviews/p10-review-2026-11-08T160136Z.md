### Medium

- **Record bodies are retyped through the file-writing tool, contradicting "never retype"** (`.agents/skills/work-chronicler-import-google-docs/SKILL.md:213`)
  - Issue: Step 8 says to "Write each record with your file-writing tool as `$STAGING/<n>.md`". The Body row (`SKILL.md:258`) requires the excerpt "verbatim: copy it from the file, never retype, reword or shorten it further", and the Rules (`SKILL.md:44-45`) allow Doc text to reach files only "through `gog`'s own output and your file-writing tool". An assistant's file-writing tool has no byte-copy mode. To write the body, the assistant must read the excerpt into the conversation and regenerate it token by token. With up to 16,384 bytes per Doc and hundreds of Docs (the journal's live run staged 223, 21 of them truncated at the cap), an assistant following the skill literally regenerates hundreds of KiB to MiB of text. That costs a lot of tokens and context compaction, and any drift (normalized quotes or whitespace, dropped lines, a silent shortening) cannot be caught: the CLI checks only the byte cap, not fidelity to the Doc. That undercuts "The Doc's own text, never a summary" (`SKILL.md:41-43`). The live walkthrough "follow[ed] the skill's steps 1–10 with a script" (implementation.md, p10 journal), so the literal assistant path was not verified.
  - Fix: Keep the body out of the generated output. In step 8, write only the frontmatter with the file-writing tool to `$READS/front.md`, ending with the closing `---` line and one blank line. Then assemble the record with `cat "$READS/front.md" "$READS/excerpt.txt" > "$STAGING/<n>.md"` (or `"$READS/doc.txt"` when not truncated). This puts no Doc text in a shell command, so it still satisfies the Rules line. The record-file reader strips exactly one leading and one trailing newline (`src/core/import/record-file.ts:51-52`), so the body equals the excerpt byte for byte. A probe in this review confirmed that a body assembled this way validates at exactly 16,384 bytes. Update the Rules line (`SKILL.md:44-45`) and the Body row (`SKILL.md:258`) to match. Optionally, have the assistant scan the excerpt file for ticket keys and PR URLs (for example with `grep -oE`) instead of reading it whole. Ticket keys and PR URLs are what end up in `mentions` anyway.

## Speculative (not findings)

These are failure modes I judged unlikely or unobserved. Under AGENTS.md "Get buy-in before speculative complexity" they are listed for the user to decide on, not fixed by default.

- **Dead-end guidance for `SOURCE_RULE` on `document.createdAt`** (`SKILL.md:292-294`). The CLI refuses a Doc whose `createdTime` is later than its `modifiedTime` (`src/core/import/sources.ts:416-421`). I confirmed this with a probe: `SOURCE_RULE` on `document.createdAt`. The skill says to "Fix that field following step 8", but step 8 just reproduces the same Drive value, so the record can never pass and blocks its chunk. That ordering can happen for files converted with a client-set modified time, but the 227-Doc live run never hit it. Cost of a fix: one sentence, either in step 6 (skip and count when `createdTime` is later than `modifiedTime`) or in step 9 (delete the record and count it as refused).
- **Manager mode reads as gog's default account without confirming it** (`SKILL.md:88-91`). If the manager's gog default is a different account (for example a personal one), the listing returns zero Docs and the import is reported as complete. Manager reading is synthetic-only, as the journal says. Cost: one step that prints the account gog reads as, plus a note to say so when nothing is listed.
- **The `BATCH_TOO_LARGE` split directory is not cleaned up** (`SKILL.md:295-296`, `SKILL.md:313-314`). The second staging directory created on a split is not one of the two directories removed in step 10. The path is effectively unreachable: 500 records of at most about 17 KiB each is far below 10,000 records and 64 MiB (`src/core/import/staging.ts:20,34`). Cost: one clause in step 10.
- **Off-by-one if `docs cat` appends a newline.** If gog adds a trailing newline to a Doc of exactly 16,384 bytes, step 7 takes the truncation path, drops the last line and sets `truncated: true`. The walkthrough confirmed byte-length truncation but not the trailing-newline behavior. The result stays valid and within the cap. Cost: none recommended.
- **Unlisted validate issue codes** (for example `SUBJECT_MISMATCH`, `DUPLICATE_IDENTITY`, `UNEXPECTED_ENTRY`, `IMPORT_IN_PROGRESS`, from `src/core/import/issues.ts:9-42`) have no specific instruction in step 9. The skill's own steps prevent them (subject copied from `show`, Docs deduplicated by `id`, `N.md`-only staging), and the Slack import skill follows the same convention. Cost: one "any other code: stop and report codes and fields" line, if wanted.
- **Titles with control characters other than tabs and line breaks** (refused by `src/core/types/imported-record.ts:174`) or longer than 1,000 UTF-16 units are not covered by the title rule's normalization. These are very rare in Drive names.
