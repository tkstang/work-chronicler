## Judgement on the Behavior Changes

- **t17, binding the cursor to the tool and filters:** sound.
  - The hash covers the normalized filters: lowercased `query`, `source`, the parsed `since`/`until` times, the uppercased `ticketKey`, the normalized `prUrl` and `attribution`. So equivalent spellings of a filter share a cursor. `limit` is left out of the hash, so the page size can change between pages, as the docs say.
  - The cursor is checked before any records are read, and a refused cursor returns an error, never a wrong page.
  - Two side effects are acceptable. Cursors issued before this change are refused, which matters to no one because the tool is unreleased. A query of `""` and an omitted query hash differently, which is harmless.
  - Documentation: the contract in `documentation/mcp-server.md` (Pages), the code comment in `search-messages.ts`, the CHANGELOG and the journal's pagination contract now agree. The journal's earlier phrase "A cursor does not carry its filters" was replaced.
  - p09's `search_documents` can reuse `pagination.ts` with its own tool name.
- **t18, refusing a non-exact date-only `until`:** sound.
  - These inputs used to be misread without any error. `2025-02-30` rolled over to Mar 2. `2025-02` and `2025` meant the start of the month or year, so almost the whole period was dropped. `Feb 28 2025` and `2025-2-28` were parsed in local time.
  - Refusing them is safer than guessing. The refusal applies only to `search_messages` and to `get_stats` with a date range, and an input with a time (`\d:\d`) still parses as before.
  - No package skill passes `until` in any of those forms. The only `until` mentions are the detect skills' "narrow with `since`/`until`" and import-slack's config range, which is not an MCP input.
  - Documented in `mcp-server.md:106-112` and the CHANGELOG.

**Observations (outside this delta, no action required for p15):**

- A timestamp without an offset (`2025-02-28T12:00`) is still read in the server's local time, as it was before p15. Probe under Chicago time: `2025-02-28T18:00:00.000Z`. The docs' example includes `Z`, and t18 covers date-only values only.
- `since` is still parsed with plain `parseAndValidateDate`, so a padded date-only `since` is read in local time. It is unchanged since before p15. p09 or a later reading-tools pass may want the same treatment.
