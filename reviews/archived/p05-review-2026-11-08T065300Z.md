### Medium

- **Concurrent `filter` runs can delete both the previous and the new subset, leaving consumers on the full work log** (`src/core/storage/filtered-subset.ts:459`)
  - Issue: After its swap, a run removes every `.filter-staging-*` and `.filter-previous-*` entry in the work-log root (lines 459-466), not only the ones it created. The race needs run A to finish its swap, then run B to move A's new `filtered/` to `.filter-previous-B`. If A's cleanup lists the root at that point, it deletes B's staging directory and `.filter-previous-B`, which holds A's subset. B's second rename then fails with ENOENT, and so does its attempt to put the previous subset back. The work log ends with no `filtered/` and no previous subset, so `getFilteredSubsetState` returns `none`, and `analyze` and the MCP server silently read the full work log. B's error message also says the previous subset "is kept at .filter-previous-…" (line 447), but that path is gone. This contradicts the phase Intent ("a failure keeps the previous subset and consumers never silently fall back to the full log") and the journal's note that under concurrent runs "state stays consistent, the losing run errors".
  - Reproduction: `/tmp/wcrev-probe/race.ts` runs two real processes, each calling `replaceFilteredSubset` on one work log. `SubsetFs` hooks only pin this legal OS interleaving, and every operation is the real node fs call. Observed: `A ok`; then `B error: … it is kept at …/.filter-previous-1a6ec9e9946054b7`; then `work log root entries: []` and `state: {"status":"none"}`. Expected: either A's subset or B's subset selected.
  - Fix: Serialize `replaceFilteredSubset` and `clearFilteredSubset`, for example with an exclusive `.filter-lock` taken by atomic `mkdir` or a hard link, as `import` already does with `.import-lock`. Alternatively, limit post-swap cleanup to the names this run created, plus leftovers that are provably stale under the lock. Add a regression test that reproduces this interleaving, using the `SubsetFs` hook pattern above or two processes. If concurrency stays unsupported, still make sure the losing run can never delete the other run's previous subset, and document the limit.

- **An unreadable `messages/<source>/` directory is treated as empty, and the previous subset is replaced without those messages** (`src/cli/commands/filter/filter.utils.ts:176`)
  - Issue: `writeFilteredSubset` reads messages through `readAllImportedRecords`. That function turns a non-ENOENT `readdir` failure (for example EACCES) into a skipped entry, `directory could not be read` (`src/core/storage/reader.ts:351`), and prints only a console warning. The filter then builds and validates a subset with zero messages and swaps it in over the previous subset, which had them. The empty `filtered/messages/` directory also hides the gap from `status`, `search_messages` and `subsetGapNote`, because the type directory exists. PR, ticket and review directories behave differently: `findMarkdownFiles` lets a `readdir` error propagate, so `filter` fails and keeps the previous subset. This breaks the phase rule to treat only a proven ENOENT as absent, and the Intent that a failure keeps the previous subset.
  - Reproduction: `/tmp/wcrev-probe/perm.mts` first filters a work log holding one message (`first subset messages: 1`), then sets `messages/slack` to mode 000 and filters again. Observed: `Warning: Skipped …/messages/slack: directory could not be read`, then `second run resolved; subset messages: 0`, then `state: selected missing: []`, with `filtered/messages/slack` absent.
  - Fix: In `writeFilteredSubset`, call `scanImportedRecords(outputDir)` directly and throw before `replaceFilteredSubset` when any skipped entry is a read failure (`directory could not be read`, `could not be read`), so the previous subset is kept. Invalid or misplaced record files can keep the current warn-and-skip behavior, which matches the PR reader. Add a mixed work-log test that injects the failure without depending on non-root `chmod`, for example with a reader seam.

- **The writing skills' preferred `search_pr_reviews` path no longer withholds reviews when the GitHub username is unknown** (`.agents/skills/work-chronicler-write-self-review/SKILL.md:90`)
  - Issue: p05 rewrote the four writing skills (`summarize-work:78`, `write-resume-bullets:77`, `update-resume:118`, `write-self-review:90`) to get review records from `search_pr_reviews` first. They say it "leaves out records written for another GitHub user". The reviewer check, including "If you cannot read the username, do not present any review file as the user's work; ask the user instead", now applies only to the "Without the MCP tool" file path (`write-self-review/SKILL.md:99`). With no configured `github.username`, which the schema allows when `orgs` is empty, `splitReviewRecordsByReviewer` counts every record as the user's (`src/core/types/pr-review.ts:102`). `search_pr_reviews` then returns another person's reviews with no `note`. The existing test `is attributed to its reviewer when the configured user is unknown` (`src/mcp/tools/tools.test.ts:723`) asserts `total: 3`, including `reviewer: 'alice'`, with no note. Under the m01 text, the agent confirmed the reviewer before citing on every path. Now an agent that follows the preferred path cites `alice`'s reviews as the user's review work in a resume or self-review. The exit evidence says "every path a skill uses to read review records (MCP or direct file) still excludes and discloses foreign-reviewer records".
  - Reproduction: `pnpm vitest run src/mcp/tools/tools.test.ts -t "configured user is unknown"`. The handler returns alice's record among results with no `note`, and none of the four skills tells the agent to check `reviewer` on the MCP path.
  - Fix: Either have `search_pr_reviews` return a `note` when `githubUsername` is unset, saying that records cannot be attributed and naming the distinct reviewers, or withhold results. Also add one line to the MCP paragraph of all four skills: when the configured username is unknown, or a result's `reviewer` differs from it, do not present the record as the user's work. Update the test at `tools.test.ts:723` to match.
