### Medium

- **A filtered subset that predates `--reviews` silently hides review records from the MCP tool and skills** (`src/mcp/server.ts:63`)
  - Issue: The MCP server reads `filtered/` whenever `filtered/pull-requests/` exists (`getEffectiveOutputDir`, `src/core/storage/paths.ts:57-70`). `filter` copies review records only when it runs (`src/cli/commands/filter.ts:335-347`). A user who ran `filter` before 0.5.0, or before their first `fetch --reviews`, therefore gets `total: 0` from `search_pr_reviews`, with nothing in the response to show why. A probe confirmed this (see Verification Commands). The skills make it worse. They say "use `filtered/pr-reviews/` when `filtered/` exists" and "If `pr-reviews/` is missing, reviews were not fetched: say so" (`.agents/skills/work-chronicler-write-self-review/SKILL.md:84-99` and the same text in the write-resume-bullets and summarize-work skills). In this state a skill tells the user they never fetched reviews when they did. `filter` also writes no `filtered/pr-reviews/` directory when no record matches, so the skills cannot tell "nothing matched" apart from "predates reviews". `status` reads the raw directory and shows the reviews, so the two surfaces disagree. This is review evidence silently missing from the subset the user selected, which Outcome 4's "never silently bypassed" principle is meant to prevent.
  - Fix: Choose one approach and test it.
    - (a) In `search_pr_reviews`, when the context is filtered, `filtered/pr-reviews/` is absent and the raw `pr-reviews/` has records, return a `note` field telling the user to re-run `work-chronicler filter` so the subset includes reviews. This needs a flag or the base dir in `ToolContext`.
    - (b) Make `filter` always create `filtered/pr-reviews/` (even when empty) so that a missing directory reliably means "subset predates reviews". Then update the three skills to say: if `filtered/` exists but `filtered/pr-reviews/` does not, the subset predates review fetching, so re-run `filter`.

    Either way, add one sentence to `documentation/commands.md` (filter section) and `documentation/mcp-server.md` saying to re-run `filter` after `fetch --reviews`. Add a case to `src/cli/commands/mixed-work-log.test.ts` with a pre-existing `filtered/pull-requests/` and no `filtered/pr-reviews/`.

- **`work-chronicler-update-resume` was not taught to cite review work** (`.agents/skills/work-chronicler-update-resume/SKILL.md:40`)
  - Issue: The p02 Intent says to "let the writing skills cite them as review work". Only `write-self-review`, `write-resume-bullets` and `summarize-work` were updated (commit 57a1470). `update-resume` writes an updated resume from the work log, and the brief's Goal says "The user needs this now to update their resume". Its data-layout tree and steps still list only `pull-requests/` and `jira/`, so the skill the user is most likely to run will ignore the review records. The journal does not record this as a deliberate scope choice.
  - Fix: Add the same "Review Work (PR Reviews the User Gave)" section and `pr-reviews/` tree entry used in `write-resume-bullets` to `update-resume`, including the leadership/collaboration placement guidance. Update the CHANGELOG line that lists the skills citing reviews. If the omission is intentional, record the reason in the p02 journal instead.

### Low

- **CHANGELOG says "on any PR" although the user's own PRs are skipped** (`CHANGELOG.md:19-21`)
  - Issue: The fetch excludes PRs the user authored (`-author:` in the query at `src/cli/commands/fetch/github/github-reviews.utils.ts:489` and the check at line 513). The journal records this as an accepted deviation, and `documentation/commands.md` says "PRs you authored are skipped". The CHANGELOG still says reviews are recorded "on any PR in your configured orgs and repos". The plan's Design bullet "regardless of the reviewed PR's age or author" has the same drift, but the journal deviation already covers it.
  - Suggestion: Reword the CHANGELOG entry to "on other people's PRs in your configured orgs and repos, however old the PR". Optionally add "(own PRs excluded; see journal p02)" to the plan's Design bullet when the plan is next amended.

- **Duplicate "incomplete results" warnings** (`src/cli/commands/fetch/github/github-reviews.utils.ts:181-183`)
  - Issue: `problems.push('GitHub search returned incomplete results.')` runs for every page of every split window that reports `incomplete_results`. A heavy reviewer can get the same warning many times per org.
  - Suggestion: Push the message once per org, for example by checking `problems.includes(...)` first or tracking a boolean in `searchReviewedPRs`. Add a test assertion that the warning appears once.

- **No automated test for re-fetching with a changed range** (`src/cli/commands/fetch/github/github-reviews.test.ts:636`)
  - Issue: The `--cache` test only re-fetches the same range. Nothing locks in `mergeEntries` keeping stored entries outside the new range, or `isRecordCurrent` refetching when `since` moves earlier. The phase relies on both for correct upserts. The probe in this review shows the behavior is correct today, but a regression would go unnoticed.
  - Suggestion: Add a test with review A in Feb and review B in Aug (PR `updatedAt` in Aug). Fetch [Jan, Jun], then [Jul, Dec], and expect reviews [A, B] with `fetchedRange.since` set to Jul. Then fetch [Jan, Dec] with `useCache: true` and expect one `listReviews` call, then zero on the next run.

- **The `search_pr_reviews` `state` filter drops every inline comment without saying so** (`src/mcp/tools/search-pr-reviews.ts:21-24`)
  - Issue: When `state` is set, `comments` is forced to `[]` (lines 55-57). The parameter description says only "Only reviews with this state", so a client asking for `CHANGES_REQUESTED` loses the inline comments that carried the requested changes.
  - Suggestion: Either extend the description ("…; inline comments are omitted when a state is given") and the golden file, or keep comments whose `reviewId` matches a review with the requested state.
