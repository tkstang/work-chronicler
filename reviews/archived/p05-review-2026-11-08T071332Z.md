### Low

- **Non-atomic lock release makes a run tell the user to delete another run's live lock** (`src/core/storage/filtered-subset.ts:477`)
  - Issue: Release calls `removeQuietly(fs, lockPath)`, which is `rmSync(recursive)` (line 178). That call unlinks `owner.json` first and then removes the directory. Between those two steps `.filter-lock` is an empty directory. A contender's `rename(claim, .filter-lock)` succeeds at that moment, because POSIX `rename` replaces an empty directory. The releasing run's `rmdir` then fails with ENOTEMPTY, and `removeQuietly` (line 545) warns `Could not remove …/.filter-lock (ENOTEMPTY); it is not used and can be deleted.`. That lock belongs to a live run. A user who follows the advice while that run is still swapping removes the only thing that stops a third run, which reopens the round-1 M1 race. The same window also refuses contenders with `…/.filter-lock exists but could not be read; … remove it and try again` (line 495). Mutual exclusion itself held in the probe: no double hold was detected.
  - Reproduction: `/tmp/wcrev2-probe/stress.ts` runs 2 real processes that loop `clearFilteredSubset` on one work log for 6 s. Its pass-through hooks only record lock entry. Observed: 8,160 successful acquisitions and 28 `WARN Could not remove .filter-lock (ENOTEMPTY); it is not used and can be deleted.` warnings. There were also 61 refusals saying the lock "could not be read", and 0 double holds. With 6 processes for 10 s: 576 such warnings and 0 double holds.
  - Suggestion: Make release one atomic step. Rename `.filter-lock` to a unique `.filter-lock.released-<runId>`, verify that it still names this run, and then remove that copy; if it names another run, rename it back. Alternatively, use the import lock's design: a single owner file taken with `link` and released with `unlink` (`src/core/import/transaction.ts:240`, `:311`). Never say "it is not used" about `.filter-lock` itself. Add a regression test that injects the empty-directory window through `SubsetFs.rm`.

- **A stale-lock takeover race lets two runs hold `.filter-lock` at once, and leaves a `.filter-lock.stale-*` behind** (`src/core/storage/filtered-subset.ts:502`)
  - Issue: Run C judges the stale owner X dead. Before C's `rename(lock, stale)`, run B takes over and acquires the lock, so C moves B's live lock aside. C sees the owner mismatch and tries to give the lock back (line 513). If run D's `rename(claim, lock)` lands in that window, D now holds the lock as well. C's give-back then fails silently, and B's owner record is stranded in `.filter-lock.stale-<id>`. B and D then build and swap at the same time, which is the round-1 M1 class: B's post-swap cleanup deleted D's staging directory. B's release only warns that the lock "no longer names this run". Nothing removes the stranded `.filter-lock.stale-*` or `.filter-lock.claim-*` entries later. The import lock cleans up its own claims and stale locks under the lock. This needs a crashed earlier run (Ctrl-C is enough) plus three runs starting within microseconds of each other, so it is very unlikely in practice.
  - Reproduction: `/tmp/wcrev2-probe/takeover3.ts`, with pass-through `SubsetFs` hooks that only pin the interleaving. Observed: `runs inside the lock at once: 2`. Then `B ok [… .filter-lock no longer names this run …]`, then `D err ENOENT … rename '.filter-staging-d…' -> 'filtered'`. Root at the end: `.filter-lock.stale-…` and `filtered`.
  - Suggestion: Serialize takeovers, for example with an exclusive `mkdir(.filter-lock.takeover)` guard held while a stale lock is judged, moved and replaced. Alternatively, have `swapInSubset` re-check that the lock still names this run immediately before its swap renames and before deleting leftovers, and abort if it does not. Remove `.filter-lock.claim-*` and `.filter-lock.stale-*` leftovers once the lock is held.

- **A lock left under another hostname or a reused PID blocks `filter` and `filter --clear` permanently, and the CLI never says how to recover** (`src/core/storage/filtered-subset.ts:425`)
  - Issue: By design, `ownerIsAlive` (line 419) respects any lock whose hostname differs from `os.hostname()` and any lock whose PID is running. Two ordinary cases hit this: a filter interrupted with Ctrl-C (no `finally` runs) before the machine's hostname changes, as macOS hostnames do with network changes, or a dead run's PID reused by another process. In both, every later `filter` and `filter --clear` fails with `LOCK_HELD`. That message says to "try again when it finishes". It does not name `.filter-lock` or say it can be removed when no filter is running. `status` reports the subset as "in use" with no mention of the lock, and still recommends `work-chronicler filter --clear`, which fails with the same message (`src/cli/commands/status.ts:53`). The removal step exists only in `documentation/commands.md`.
  - Reproduction: In a temp home, run `pnpm cli filter -c <cfg> --org acme`. Then create `<work-log>/.filter-lock/owner.json` with `{"version":1,"pid":4242,"hostname":"Old-Hostname.local","startedAt":1,"runId":"x"}`. Run `pnpm cli filter -c <cfg> --org acme` and `pnpm cli filter -c <cfg> --clear`: both print `Error: Another \`work-chronicler filter\` run is changing … try again when it finishes. The subset was not changed.`. `pnpm cli status -c <cfg>`prints`Filtered subset: in use … Run \`work-chronicler filter --clear\` …`.
  - Suggestion: Include the lock path and its owner (hostname, PID, start time) in `LOCK_HELD`, and add "if no filter is running, remove <path> and try again", matching the unreadable-lock message at line 495. Have `status` print a line whenever `.filter-lock` exists, not only in the interrupted state. Cover both in the existing other-machine lock test.
