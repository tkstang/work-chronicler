### Low

- **`get_stats` unavailability during an import is stale in `commands.md` and absent from the CHANGELOG** (`documentation/commands.md:125`)
  - Issue: Since p15-t11, `get_stats` reads imported records even when it returns the cached `stats.json` (`src/mcp/tools/get-stats.ts:46-71`). So it now returns the import-unavailable error during an import in every mode. `documentation/mcp-server.md:32-37` was updated to say this, but `documentation/commands.md:125-127` still says "`get_stats` when it computes stats". The p15-t11 CHANGELOG entry (`CHANGELOG.md:88-91`) describes the refreshed counts but not this user-visible change, which the journal lists as an accepted concern. AGENTS.md makes code the source of truth for docs.
  - Fix: In `commands.md`, change "and `get_stats` when it computes stats" to "and `get_stats`". In the CHANGELOG, add one sentence to the p15-t11 entry: without a date range, `get_stats` now also returns the import-unavailable error while an import is storing a batch.
- **The Pages contract says any cursor not from `nextCursor` is refused, but only malformed cursors are** (`documentation/mcp-server.md:157`)
  - Issue: `decodeCursor` (`src/mcp/tools/search-messages.ts:59-79`) accepts any base64url JSON `[finite number, string]`. I ran a probe with the forged cursor `base64url("[0,\"\"]")`: it returned a normal empty page, not an error. The journal's contract says "foreign cursors refused", and p09's `search_documents` will reuse the same `[time, key]` shape. A `search_documents` cursor would then be accepted by `search_messages` as a position, against the documented contract. The effect is harmless today (a forged position only selects where the page starts), but the contract that later tools are told to copy is wrong.
  - Fix: Either tag the cursor with its tool (for example encode `["m", time, key]`, check the tag in `decodeCursor`, and make p09 use its own tag) and add a test that a cursor from another tool is refused, or reword the docs and journal to "A malformed cursor is refused".
- **A date-only `until` with surrounding whitespace is read as the end of the local day, not the UTC day** (`src/mcp/tools/types.ts:102`)
  - Issue: `parseUntilDate` tests `DATE_ONLY` against `dateStr.trim()` but parses the untrimmed string. V8 parses `" 2025-02-28"` as local time. Probe with `TZ=America/Chicago`: `parseUntilDate('2025-02-28')` gives `2025-02-28T23:59:59.999Z`, but `parseUntilDate(' 2025-02-28')` gives `2025-03-01T05:59:59.999Z`, so messages from the next UTC day are included. The input is unlikely from an assistant, but the documented "whole UTC day" guarantee does not hold for it.
  - Suggestion: Trim once and parse the trimmed value (`const s = dateStr.trim(); const date = parseAndValidateDate(s, fieldName);`), or skip trimming so that a padded date is treated as a timestamp. Add a test case with surrounding whitespace.
- **Two skills that point at `search_messages` do not mention paging** (`.agents/skills/work-chronicler-detect-projects/SKILL.md:67`)
  - Issue: p15-t15 added the paging instruction to the four writing skills, but `work-chronicler-detect-projects` (line 67) and `work-chronicler-detect-themes` (`SKILL.md:87`) also tell the assistant to use `search_messages`. If the assistant reads only the first page, a large import is silently cut to roughly 64 KiB of the newest messages. The tool description mentions `nextCursor`, which reduces the risk, and these skills use messages only to corroborate.
  - Suggestion: Add the same sentence to both skills ("Results come in pages: while `nextCursor` is not null, call `search_messages` again with the same filters and `cursor` set to it"). Consider adding "narrow with `since`/`until` or `ticketKey` first" wherever an unfiltered walk would pull a whole large import into context.
- **The workspace-label host check refuses permalinks on a sibling host in an Enterprise Grid org** (`src/core/import/sources.ts:178`)
  - Issue: `onConfiguredWorkspace` accepts only `<label>.slack.com` and `<label>.enterprise.slack.com`. The setup-slack skill (`SKILL.md:65-69`) derives the label from one permalink returned by the connector. In a Grid org, the connector can return permalinks on another workspace's host (`team-a.slack.com`) as well as the org host (`org.enterprise.slack.com`). If the configured channels belong to different workspaces in the org, some records will now fail with "must be a permalink on the configured Slack workspace". The failure is loud (`validate` reports it, nothing is stored), and the check is what the plan and CodeRabbit item asked for. But the user has no recovery unless a tool shows the `E…` org ID, which accepts any host.
  - Suggestion: State the limitation in `documentation/commands.md` (Slack records) and in the setup-slack skill: with a URL label, configure only channels whose permalinks use that host, or configure the `E…`/`T…` ID when a tool shows it. Optionally append that hint to the refusal message. A code change is not required.
