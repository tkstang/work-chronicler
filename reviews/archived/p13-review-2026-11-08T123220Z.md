### Medium

- **`status` says a filter is replacing `filtered/` when an import holds the work-log lock** (`src/cli/commands/status.ts:221`)
  - Issue: `describeSubset(outputDir, lock.length > 0)` treats any holder of the shared lock as a running filter. Since p13 an `import` holds `.import-lock` and `.filter-lock` too. If `filtered/` is interrupted (an earlier `filter` crashed between renames) while an import holds the lock or a crashed import left it, `status` prints "a `work-chronicler filter` run is replacing filtered/ … until it finishes or the lock is removed" (`status.ts:72-75`). No filter is running, and the subset stays interrupted after the import finishes, so "wait for it" never resolves. `getFilteredSubsetState` already distinguishes this case: its `locked` field is true only for a `filter` holder (`filtered-subset.ts:334-336`), so the MCP server tells the user to run `filter` again. `status` and MCP now disagree. Before p13 the two checks agreed, because only `filter` held `.filter-lock`.
  - Reproduction: a work log with `.filter-previous-old/` and no `filtered/`, plus `.import-lock/` and `.filter-lock/` whose owner has `command: "import"`. A probe in a temporary export of the head tree confirmed `getFilteredSubsetState(w)` returns `{status:'interrupted', locked:false}` while `readWorkLogLockHolders(w).length === 2`, so `status` takes the "filter is replacing" branch.
  - Fix: In the interrupted branch, use the subset state's own `locked` (`state.status === 'interrupted' && state.locked`) instead of the `locked` parameter. Keep the parameter for the `--clear` advice, which is correctly hidden while any run holds the lock. For the import-held case, say that the subset was interrupted by an earlier filter and that `filter` will restore it once the import (named below) finishes. Add a case to the existing "filter is refused while an import holds the work-log lock" test in `mixed-work-log.test.ts` with a `.filter-previous-*` directory and no `filtered/`.

### Low

- **Stale rationale comment in `inspectImportState`** (`src/core/import/transaction.ts:556`)
  - Issue: The comment says "a filter holding it changes no record". Since p13-t03, a `filter` holding the lock rolls back or completes an interrupted import's records (`settleInterruptedImport`). Behavior is still safe, because `.import-transaction/` exists throughout that recovery and `validate` then reports `RECOVERY_REQUIRED`. The stated reason is false, though, and a future change could rely on it.
  - Fix: Reword it, for example: "A filter changes records only while finishing an interrupted import, and `.import-transaction/` exists throughout (reported below as RECOVERY_REQUIRED), so only an import's (or an unreadable) lock is in progress."

- **Docs present reboot detection as universal, but the boot ID exists only on Linux and macOS** (`documentation/commands.md:262-264`)
  - Issue: `systemBootId()` returns null on every platform other than Linux and macOS (`work-log-lock.ts:166-188`). There, `ownerIsAlive` judges an owner by its process alone, so a lock left before a reboot whose PID was reused is held until it is removed by hand. That is the same accepted behavior as a 0.6.0 lock. `commands.md:262-264`, `commands.md:466-468` and `CHANGELOG.md:40-44` say a lock from before a reboot "is still taken over even when its process ID is in use again", without qualification. The journal's accepted concerns cover only 0.6.0 locks.
  - Fix: Qualify the docs and CHANGELOG, for example: "(Linux and macOS record a boot ID; elsewhere, and for 0.6.0 locks, a lock is kept while a process with its ID runs)". Alternatively, record it as an accepted concern in the p13 journal.

- **`commands.md` attributes `IMPORT_IN_PROGRESS` to both refusal directions** (`documentation/commands.md:258`)
  - Issue: "`import` is refused while a filter runs, and the other way round (`IMPORT_IN_PROGRESS`, naming …)" implies that `filter` also reports `IMPORT_IN_PROGRESS`. `filter` raises `FilterInProgressError` with a prose message (`filtered-subset.ts:531-561`). Only `import` uses the code.
  - Fix: Attach the code to the import direction only, for example: "`import` is refused while a filter runs (`IMPORT_IN_PROGRESS`), and `filter` while an import runs; each names the command, process and host holding the lock."

- **Settle warning prints the raw enum "rolled-back"** (`src/core/storage/filtered-subset.ts:658`)
  - Issue: The warning reads "An interrupted import was rolled-back before filtering". The interpolated outcome is the enum value, not prose. The mixed-work-log test pins this wording (`mixed-work-log.test.ts:842-845`).
  - Fix: Map the outcomes to prose (`discarded`, `rolled back`, `completed`) and update the test expectation.

## Adversarial Notes (checked, no finding)

- Partial acquisition: when the second name fails, or `acquireLockName` throws, the first name is released (`work-log-lock.ts:411-423`), and the "releases the first name when taking the second throws" test fails without it. Reverse release order is covered incidentally: forward order fails "releases by moving the lock aside first…".
- Interaction with 0.6.0: v0.6.0 uses the same claim-rename and per-name takeover-guard protocol (no diff between v0.6.0 and the base `work-log-lock.ts`). Its default-stripping `z.object` parses 0.7.0 owners that have `bootId` and `command`. A 0.6.0 `filter` is refused by `.filter-lock`, and a 0.6.0 `import` by `.import-lock`. A 0.6.0 run can still misjudge a live 0.7.0 owner after a clock jump. That cannot be fixed from 0.7.0, and it needs both mixed versions and a clock jump.
- Boot ID: `sysctl -n kern.bootsessionuuid` returns a UUID on this macOS host, and a probe confirmed that `systemBootId()` returns a UUID. When the current boot ID is null, the owner is judged by its process alone, which is conservative.
- Reader soundness: records are one directory level deep (`getImportedRecordSegments`), and every directory an import changes (`<type>/` and `<type>/<source>/`) is in the marks. An import that runs entirely between the first pending check and the before-marks yields a consistent snapshot. Any later change either leaves `.import-transaction/` present at the second check or changes the marks. The only remaining gap is coarse-timestamp filesystems, which is documented and accepted. All imported-record readers (`search_messages`, `get_linked_work`, `get_stats`, `analyze`, `analyze reports`, `link`, `status`, `filter`) go through `scanImportedRecords`, and no reader path bypasses it.
- `validate` with a filter recovering: `.import-transaction/` exists during recovery, so `validate` reports `RECOVERY_REQUIRED` (see L1 for the comment).
