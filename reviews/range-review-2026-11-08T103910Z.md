### High

- **H1. Preserve recovery evidence when a missing journal contradicts applying markers** (`src/core/import/transaction.ts:961`)
  - Issue: Every proven missing `journal.json` is classified as interrupted preparation, and `discardTransaction` deletes the transaction, including its backups, without checking whether records were already applied. With two existing records, interrupt immediately after renaming the first replacement into place, then remove the journal while leaving the nonempty `applying/` directory and both backups. The next empty import returns `ok: true`, reports `discarded` with zero records, deletes the transaction, and leaves the first record new and the second old. The intact-journal control rolls both back correctly. This trigger requires missing/corrupted bookkeeping after interruption; a process interruption alone did not reproduce it.
  - Impact: Ambiguous recovery is reported as successful, and the old version needed to restore the partially applied batch is destroyed. This violates p04's fail-closed recovery contract and T17 in the recorded threat matrix.
  - Fix: Treat a missing journal with evidence that application began as `RECOVERY_CONFLICT` and retain all transaction contents. Discard only a state that can be established as pre-commit preparation. Add a control for safe unfinished preparation and a regression for a missing journal with applying markers and a partially updated batch.

### Medium

- **M1. Recheck unchanged members before accepting the complete import batch** (`src/core/import/transaction.ts:1175`)
  - Issue: `commitImportPlan` removes every `unchanged` record from its verification set. In the existing mixed scenario, delete record 3, planned unchanged, at the established pre-transaction `mkdir` hook. Import still updates record 1, creates record 2 and returns `ok: true` with `unchanged: 1`, although record 3 is absent. Deleting the planned-update record at the same hook correctly returns `CHANGED_DURING_IMPORT`. The omission lasts throughout preparation and commit, beyond the documented final-check race window.
  - Impact: A successful result does not establish that all records in the accepted batch exist with their staged contents, contrary to p04's whole-batch and changed-path guarantees.
  - Fix: Keep unchanged records in the verified read set, including directory identity and content checks, and verify them before accepting the batch. On conflict, preserve the external edit/deletion and undo this batch's changes. Cover unchanged-member deletion/edit during preparation and retain the valid idempotent control.

- **M2. Report post-publication enumeration failure as a cleanup warning** (`src/core/storage/filtered-subset.ts:678`)
  - Issue: After publishing the new `filtered/` and deleting the previous subset, `findLeftovers` can throw on `readdir` EIO. The replacement promise then rejects, although the new subset is selected and the previous copy is gone. The CLI's catch at `src/cli/commands/filter/index.ts:130` tells the user that the filtered subset was not changed. Injecting EIO only on root enumeration after staging is renamed to `filtered/` reproduces this; the no-error control publishes successfully.
  - Impact: A command that reports failure has changed the effective evidence selection, misleading the user about which records subsequent analysis and MCP calls use.
  - Fix: Once publication succeeds, catch leftover-enumeration failures and return a cleanup warning, as removal failures already do. Add this failure control alongside the existing post-publication cleanup tests.
