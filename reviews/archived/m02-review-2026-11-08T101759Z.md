**H1: Stale import-lock takeover can admit two live importers** (`src/core/import/transaction.ts:503`; related `:514-523`).

A contender reads the dead lock owner at line 481, then renames whatever currently occupies `.import-lock` at line 503. Another contender may already have taken over and returned a valid live lock in between. Moving that live lock aside exposes an absent lock name to a third importer. The post-rename owner check detects the substitution, but restoring the live lock then fails with `EEXIST` because the third importer already acquired it. Both live importers have returned successful acquisitions. The rejected contender then unlinks the displaced live lock.

The reproduction uses the real filesystem and the existing `ImportFs.rename` seam only to schedule normal operations. Observed result at the reviewed build:

```json
{
  "A_acquired": false,
  "B_acquired": true,
  "C_acquired": true,
  "onDisk": "C",
  "A_issues": "IMPORT_IN_PROGRESS",
  "A_warnings": ["could not restore another import's lock (EEXIST)"]
}
```

**One-line reproduction:** Seed a dead lock; pause A after its owner read; let B take over; resume A's rename of B's lock; let C claim the freed name before A restores it. B and C both return locks.

**Impact:** `runImport` trusts this acquisition before cleanup, recovery and commit against the one shared `.import-transaction` directory. Two admitted live callers can operate on each other's bookkeeping or start recovery of a still-running import. The public one-import-per-work-log contract in `documentation/commands.md:242` is not enforced. The probe proves double admission, not a particular lost-record outcome.

The p04 journal explicitly lists simultaneous stale-lock takeover as a residual race. This finding is the demonstrated contract failure, not a request for speculative hardening or elimination of every filesystem race. The filter implementation already serializes stale takeover separately, showing this race is avoidable within the existing architecture.

**Fix guidance:** Serialize stale import-lock takeover, recheck the observed owner under that serialization, and never temporarily remove a replacement owner's live lock. Add a deterministic regression covering the three-contender schedule while retaining the successful ordinary stale takeover and live-owner refusal controls.
