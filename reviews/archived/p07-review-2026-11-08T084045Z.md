### Low

- **Labelled link markup without `//` (mailto, tel) passes the body rule** (`src/core/import/sources.ts:161`)
  - Issue: The two link patterns (`sources.ts:161-162`) require `scheme://`.
    Slack writes a typed or formatted email link as
    `<mailto:addr|label>`, and a phone link as `<tel:…|label>`, so these
    raw `<url|label>` tokens are accepted and stored verbatim. The label can
    be custom link text, such as another person's name. The CHANGELOG entry
    (`CHANGELOG.md:38-41`) says bodies are free of raw link markup
    (`<url|label>`). The skill's link row (`SKILL.md:189`) covers only
    `https`, so nothing tells the agent to rewrite a mailto token. The
    rule's own doc comment and `documentation/commands.md` name only
    `https` links. The defect is the gap between the general claim and what
    the code checks.
  - Reproduction: run `runImport({ mode: 'validate', … })` on the synthetic
    record (`messageFrontmatter(1)`, `SYNTH_SOURCES`) with body
    `ping <mailto:sam.other@example.com|Sam Other>`. The result is
    `{"ok":true,"issues":[]}`. The same body with `https://` instead of
    `mailto:` is refused.
  - Fix: Widen the labelled-link pattern to any `<scheme:…|…>` token, for
    example `/<(?:mailto|tel):[^\s|>]*(?:\|[^>]*)?>/i`, or a general
    `/<[a-z][a-z0-9+.-]*:[^\s|>]+\|[^>]*>/i`. Then add a mailto case to the
    refused table in `slack-rules.test.ts:290` and a row to the skill's
    markup table: write the address alone and drop the label. If mailto is
    deliberately out of scope, narrow the CHANGELOG wording to the forms
    the code checks instead.

- **Some refused forms have no rewrite path in the skill, and `<!…>` refuses ordinary text** (`src/core/import/sources.ts:160`)
  - Issue: On a `SOURCE_RULE` on `body`, the skill (`SKILL.md:230-233`)
    tells the agent to rewrite with the step-6 markup table. That table
    (`SKILL.md:186-191`) has rows only for user mentions, `https` links,
    channel links and `<!here>`, `<!channel>` and `<!everyone>`. The rule
    also refuses `<!subteam^S…|@team>`, which `documentation/commands.md`
    lists explicitly, and `<!date^…|…>`. User-group mentions are common in
    work channels, and the skill gives no target form for either. Separately,
    `/<![a-z][^>]*>/i` matches any `<!word…>`, so ordinary text such as
    ``use `<!DOCTYPE html>` at the top`` is refused. No table row applies,
    so the only way through is to alter the user's verbatim text or drop the
    message, and one such message keeps the whole batch refused. Whether
    connector `Text` ever carries a literal `<!DOCTYPE` depends on whether it
    returns `&lt;` entity-decoded text, which this review could not check
    without Slack tools. The skill-table gap does not depend on that.
  - Reproduction: run `runImport` validate on the synthetic record with
    body `<!subteam^S0X|@billing-team> please look` or
    ``use `<!DOCTYPE html>` at the top``. Both return
    `ok:false, [["SOURCE_RULE","body"]]`, and `SKILL.md:186-191` has no
    row for either.
  - Fix: Add a skill-table row for `<!subteam^…|@team>` →
    `@team` (and `<!date^…|text>` → the fallback text or drop it). Narrow
    the special-mention pattern to the Slack forms, for example
    `/<!(?:here|channel|everyone|subteam\^|date\^)[^>]*>/i`, and add
    `<!DOCTYPE html>` to the accepted cases in `slack-rules.test.ts:303`.
    Or keep the broad pattern and tell the skill to skip a message it
    cannot rewrite without changing the user's words.
