### Low

- **L1 — Fixed here-document delimiter leaves a forbidden multi-line reason able to run commands** (`.agents/skills/work-chronicler-setup-slack/SKILL.md:152`)
  - Issue: The command uses a constant delimiter, `<<'WC_REASON'`. If the agent writes a reason that spans lines and one of those lines is exactly `WC_REASON`, the here-document ends early and the shell runs the lines after it. Probe: reason `ok\nWC_REASON\ntouch "$MARK"` created the marker in `/bin/sh`, `/bin/bash` and `/bin/zsh`, and the channel was stored with reason `ok`. Two skill rules guard this: line 161 ("The reason is one line and never `WC_REASON` by itself") and line 143 ("Never copy a topic or purpose into the reason unchanged"). So the path needs the agent to break both rules, for example by pasting a hostile multi-line channel purpose. That is far narrower than the 0.6.0 apostrophe bug, but it is the same class of failure, on a security-relevant boundary that depends only on model compliance. A reason that is exactly `WC_REASON` (no extra lines) is harmless: the CLI refuses the empty reason, and the shell reports `WC_REASON: command not found` (exit 127).
  - Fix: Make the delimiter impossible to predict from Slack content. Tell the agent to pick a fresh one per command, such as `WC_REASON_<8 random hex digits>`, used on both lines. Or, where the host has a file-writing tool, prefer writing the reason to a temporary file and passing `--reason-file <path>`, so the reason never passes through a shell parse. Also tell the agent to check the agreed reason has no line break before running. Optionally, extend `skillChannelAdd` in `src/cli/commands/slack/slack.test.ts` to show that a multi-line reason is refused or cannot escape.

- **L2 — `--reason-file` reads without a size limit and silently replaces invalid UTF-8** (`src/cli/commands/slack/channels.ts:42`)
  - Issue: `readFileSync(file === '-' ? 0 : file, 'utf-8')` loads the whole input before the 200-character check, so `--reason-file /dev/zero` or a very large file grows memory without bound. Invalid UTF-8 bytes are decoded to U+FFFD, which `ReasonSchema` (`src/core/types/slack.ts:67-72`) accepts. Probe: reason bytes `caf\xff` were stored as `caf�` with exit 0. The docs say "The text is used as it is" (`documentation/commands.md:383`), but the schema also trims surrounding spaces (probe: `   padded reason   ` was stored as `padded reason`) and invalid bytes are replaced.
  - Fix: Read at most a small bound, for example 4 KiB, with `openSync`/`readSync`, or use the existing `ImportFs.readFile(path, maxBytes)`. Refuse a larger input. Decode with `new TextDecoder('utf-8', { fatal: true })` and refuse invalid UTF-8 with the existing "The config was not changed" message. Change the docs to "used without shell quoting; surrounding spaces and one trailing line break are dropped".

- **L3 — User-change guard is not serialized with a running import** (`src/core/config/slack-config.ts:171`)
  - Issue: `checkWorkLogAuthors` scans the work log without the work-log lock. `runImport` checks the staged batch against settings it read at CLI start (`src/core/import/index.ts:106-112`) and takes the lock only when it commits (`:146`). Consider this sequence: an import starts for user A with channels configured; the user removes the channels and runs `slack configure --user B` while the import is still planning. The scan sees no `.import-transaction/` and no A messages yet, so it passes, and the import then commits A's messages under a config that now names B. This is the mixing t09 exists to prevent. The window needs concurrent manual commands, and the journal already accepts a similar bypass (editing `slack.user` by hand), so the risk is low.
  - Fix: Either hold the shared work-log lock (`src/core/storage/work-log-lock.ts`, as `import` and `filter` do) across the author scan and the config rename for a user change, or have `import` re-read the subject's Slack settings under its lock before committing. Otherwise, record this as an accepted concern in the p16 journal next to the hand-edit bypass.
